# Partitioning by SYSTEM_TIME

## What is partitioned, and why that table

A system-versioned table keeps every superseded row version. Most queries, however, ask for the *current*
state, and old history is often subject to a retention policy. MariaDB therefore offers a partitioning scheme
dedicated to versioned tables:

```sql
CREATE TABLE page_mirror (
  article_id INT UNSIGNED NOT NULL, rev_id BIGINT UNSIGNED NOT NULL, rev_timestamp DATETIME NOT NULL,
  sha1 CHAR(40) ..., size_bytes INT UNSIGNED NOT NULL DEFAULT 0,
  row_start TIMESTAMP(6) GENERATED ALWAYS AS ROW START,
  row_end   TIMESTAMP(6) GENERATED ALWAYS AS ROW END,
  PERIOD FOR SYSTEM_TIME (row_start, row_end),
  PRIMARY KEY (article_id)
) WITH SYSTEM VERSIONING
  PARTITION BY SYSTEM_TIME INTERVAL 1 YEAR STARTS TIMESTAMP '2021-01-01 00:00:00' AUTO;
```

* The **`CURRENT`** partition (`pn`) holds the rows with `row_end` = max: one row per article.
* **History** partitions hold superseded versions, routed by **`row_end`** (the moment a version stopped
  being current) into yearly ranges: `p0` (ended before 2022), `p1` (2022), … `AUTO` creates the next partition
  when time moves past the last one.

The partitioned table is **`page_mirror`**, the one-row-per-article table that is `UPDATE`d for every edit and
whose system time equals Wikipedia time (by replay). That is the shape in which system history really
grows: 64,753 row versions for 196 current rows (measured after the replay). Partitioning `article_history` would not help:

* its system history only contains *superseded beliefs* (at most one per article and sync step: 783 rows),
  while its current rows are the whole timeline (64,753). There is almost nothing to separate;
* partitioned InnoDB tables cannot take part in foreign keys (error 1506 / errno 150, verified). The
  constraints of `article_history` (FKs to `revisions` and `articles`) are worth more than partitioning.

`page_mirror` is a rebuildable projection of `revisions`, so losing FKs there costs nothing.

The other natural temporal dimension, **application time** (`PARTITION BY RANGE COLUMNS(valid_from)` on
`article_history`), was also considered. MariaDB accepts range partitioning on a versioned table, but every key
would have to include `valid_from`, foreign keys would again be impossible, and the main query (one article,
one instant, served by a 1-row index probe) has nothing to gain from pruning. It is not used.

## What partitioning buys, measured

All numbers are in `benchmarks/reports/latest.md` (generated by `npm run benchmark`); the README (§9) summarises
them. Headline results on 1,036,048 row versions: current-state scan 184 ms → 1.1 ms with yearly partitions,
`AS OF` a recent instant 195 ms → 37.5 ms, `AS OF` an old instant unchanged (~240 ms), monthly partitions 4× the
file size of yearly ones. The partition benchmark
uses a **derived stress dataset**: K copies of the real `page_mirror` history with shifted article ids and
unchanged timestamps (so the temporal distribution is real), loaded into three tables with identical rows:
unpartitioned, yearly and monthly partitions. Results are compared with the unpartitioned table and must
return identical answers.

What to look for in the report:

1. **Current-state queries** (`SELECT … FROM t` without `FOR SYSTEM_TIME`): the partitioned tables read only
   `pn`. On the unpartitioned table, InnoDB must walk past history versions. Point lookups by primary key are
   fast either way, while scans of the current state are where the difference shows.
2. **`AS OF T`**: MariaDB prunes history partitions whose upper bound is `<= T`, since all their rows ended
   before `T`. Pruning is **asymmetric**: an instant in 2026 reads 1–2 partitions, while an instant in 2021
   reads all of them. Partitioning by `row_end` cannot prune on `row_start`.
3. **`BETWEEN` / `ALL`**: `ALL` reads everything by definition; `BETWEEN a AND b` prunes partitions that ended
   before `a`.
4. **Retention**: `ALTER TABLE … DROP PARTITION p0, p1` removes years of history by dropping files, while
   `DELETE HISTORY … BEFORE SYSTEM_TIME` deletes row by row. The benchmark times both.
5. **Granularity**: monthly partitions prune more precisely but multiply files and per-partition overhead
   (open handles, statistics, `AUTO` DDL). Yearly partitions are the default here.

## Maintenance implications

* **AUTO** creates partitions during DML (an implicit DDL step). On a busy table, consider pre-creating
  partitions (`PARTITIONS n`) during maintenance windows.
* **Retention** is the main operational benefit: dropping the oldest history partitions is cheap and does
  not fragment the table. Only history partitions can be dropped, never `CURRENT`.
* **No FKs** on partitioned tables (see above), and explicit partition selection cannot be combined with
  `FOR SYSTEM_TIME` (error 4142).
* **Growth**: history grows with the edit rate, and every version is a full row copy. With the text inline, as in
  the naive design, that is a full article per edit; the measured cost is in the benchmark report
  (“full text inside the system-versioned row”). This is why `page_mirror` references texts by SHA-1 and the
  texts themselves live in a deduplicated, delta-friendly compressed store.
* **Statistics**: `ANALYZE TABLE` after large replays keeps `TABLE_ROWS` estimates and optimizer statistics
  meaningful; the replay script runs it.

## How the strategy behaves as history grows

Yearly partitions keep the `CURRENT` partition at one row per article regardless of how much history
accumulates, so current-state queries stay flat. `AS OF` cost grows with the number of partitions that overlap
`[T, now]`, so queries about the recent past stay cheap while queries about the distant past cost more.
That is a reasonable trade-off for a time machine, where the far past is usually also queried less often.
Retention (dropping the oldest partitions) bounds the total.
